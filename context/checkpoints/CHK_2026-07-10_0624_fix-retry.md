## ✅ Lo que se hizo

### Cambios en `index.html` (refactor de `api.request` L3946)

Refactor del método `request` del objeto `api` para añadir reintentos con backoff exponencial. Implementación basada en §5 de la SPEC (referencia canónica, copiada con marcas de agua `FIX-20260710-08`).

**Estrategia de reintentos:**

| Caso | ¿Reintenta? | Razón |
|---|---|---|
| GET + network error (`Failed to fetch`) | ✅ Sí, hasta 3 intentos | Transitorio (WiFi inestable, cold start Railway) |
| GET + HTTP 5xx (500, 502, 503, 504) | ✅ Sí, hasta 3 intentos | Servidor temporalmente caído |
| GET + HTTP 429 (Too Many Requests) | ✅ Sí, hasta 3 intentos | Rate limit transitorio |
| GET + HTTP 4xx (400, 401, 403, 404) | ❌ No | Error del cliente, definitivo |
| POST/PUT/DELETE (cualquier status) | ❌ No | Evita duplicados (ventas, stock, citas) |

**Configuración:**
- `maxAttempts = 3` para GETs, `1` para otros métodos
- `backoffMs = [0, 1000, 2000]` → espera 1s antes del 2º intento, 2s antes del 3º
- Log con `console.warn('[API] Reintento X/Y ...')` cada reintento
- Sin librerías externas (implementación manual con `setTimeout`)

### Logs emitidos

| Momento | Prefijo | Ejemplo |
|---|---|---|
| Antes de cada reintento | `[API] Reintento X/Y` | `[API] Reintento 2/3 para GET /inventory tras 1000ms` |
| Network error transitorio | `[API] Network error en` | `[API] Network error en GET /inventory: Failed to fetch` |
| Reintentos agotados | `[API] Sin conexión tras N intentos` | `[API] Sin conexión tras 3 intentos, usando datos locales` |

## 🔍 Self-review manual

### FIX-08

1. ✅ ¿Los reintentos solo se aplican a GETs?
   - Verificado: `const isRetryable = method === 'GET'; const maxAttempts = isRetryable ? 3 : 1;`
   - POST/PUT/DELETE tienen `maxAttempts = 1` (sin retry). Crítico: un retry en POST `/sales` duplicaría ventas.
2. ✅ ¿Los 4xx (excepto 429) NO se reintentan?
   - Verificado: `if (resp.status >= 400 && resp.status < 500 && resp.status !== 429) { throw ... }`
   - Solo 5xx y 429 caen al `if (attempt < maxAttempts) continue;`
3. ✅ ¿El backoff es 1s + 2s = 3s total?
   - Verificado: `const backoffMs = [0, 1000, 2000];` → espera 0ms (1er intento), 1000ms (2º), 2000ms (3º). Total máximo de espera adicional: 3s. Aceptable per §8 de SPEC.
4. ✅ ¿El log es claro y útil?
   - 3 niveles: Reintento (info), Network error (causa), Sin conexión (agotado). Cada uno identifica método, path y contexto suficiente para debugging.
5. ✅ ¿Comportamiento intacto para errores 4xx y network agotado?
   - 4xx (excepto 429): throw inmediato con mensaje del backend (igual que antes).
   - Network agotado tras 3 intentos: throw con el último error + log de "usando datos locales" (preserva el comportamiento existente que ya tenía el código original).

### General

- ✅ Riesgo de regresión: bajo. POST/PUT/DELETE mantienen exactamente 1 intento (mismo comportamiento que antes). GET añade reintentos solo en errores transitorios.
- ✅ Referencias muertas: ninguna. `api.request` es el único punto de entrada de fetch del frontend (verificado en L3983-L4003).
- ✅ Side effect preservado: el borrado de JWT en 401 sigue ocurriendo antes del throw (no se reintenta el 401).
